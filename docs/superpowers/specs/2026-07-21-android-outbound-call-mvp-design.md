# Android SIM 外呼原型设计

## 1. 目标

在 iQOO Neo8 Pro 上实现一个独立的 Java 原型，跑通以下闭环：

1. 测试页面创建单个外呼任务。
2. Android App 自动领取任务并使用手机 SIM 卡拨号。
3. 人工通过手机完成本次通话，OriginOS 自动录制全部通话。
4. 挂断后，App 匹配并上传本次通话录音。
5. Java 服务端完成语音转写，并调用公司可用的 GPT-5.5 接口进行结构化判断。
6. 测试页面实时显示任务、通话、录音、转写和模型分析状态。

本原型不接入公司现有系统，不提供登录、权限管理、批量任务或正式运营后台。原型验证通过后，再设计内部系统集成和 SIM 网关机器人通话。

## 2. 已确认条件

- 测试设备为 iQOO Neo8 Pro。
- OriginOS 已开启“所有通话自动录音”，并能够生成双方通话录音。
- 手机可作为专用测试设备，外呼期间保持解锁、联网、插电且 App 常驻前台。
- 公司已有服务器资源和 GPT-5.5 模型接口。
- 第一阶段允许由人工在电话接通后交流；复杂单据仍由人工判断和处理。
- 手机端与测试服务端均优先使用 Java。

## 3. 范围

### 3.1 首版包含

- 单号码任务创建。
- 手机定时领取任务。
- Android 直接拨号。
- 通话状态监听。
- OriginOS 录音文件发现、匹配和上传。
- 找不到录音时的人工文件选择入口。
- 服务端语音转写适配器。
- GPT-5.5 分析适配器。
- 结构化分析结果。
- 无登录的实时测试页面。
- 失败原因展示和安全重试。

### 3.2 首版不包含

- AI 在 SIM 通话中实时听说。
- 自动播放机器人话术。
- 批量连续拨号。
- 自动挂机策略。
- 正式 CRM 或催收系统集成。
- 多租户、账号、角色和登录。
- 公网部署。

## 4. 技术约束

普通 Android 第三方应用不能取得仅授予系统组件的通话音频特权权限，也不能稳定地将程序音频注入 SIM 通话线路。因此，首版由 OriginOS 系统拨号器负责通话与录音，Android App 只负责拨号控制、状态监听、录音文件匹配和上传。

录音目录和存储权限可能随 OriginOS 版本变化。首版先探测设备实际录音位置；若目录不能被普通 App 直接读取，则使用 Android 系统文件选择器让测试人员选择本次录音。该降级方案仍能验证上传、转写和模型分析链路。

## 5. 总体架构

### 5.1 Android App

职责：

- 生成并持久化唯一设备 ID。
- 在前台运行并定时向服务端领取一条任务。
- 检查电话、通话状态和文件访问所需权限。
- 使用 SIM 卡直接拨号。
- 监听拨号、响铃、接通和挂断状态。
- 挂断后等待系统写完录音文件。
- 根据号码、通话开始时间、挂断时间和文件修改时间匹配录音。
- 上传录音和通话元数据。
- 在失败后保留本地状态并执行受控重试。

### 5.2 Java Spring Boot 服务端

职责：

- 提供测试任务创建、领取和状态更新接口。
- 防止同一任务被多个设备重复领取。
- 接收录音文件并保存原始文件。
- 调用语音转写接口。
- 调用 GPT-5.5 并校验结构化输出。
- 保存任务事件、转写、分析结果和错误。
- 通过 SSE 向测试页面推送最新状态。

模型地址、密钥和提示词只保存在服务端，不写入 APK 或网页。

### 5.3 实时测试页面

页面不提供登录，只允许本机或测试局域网访问。页面包括：

- 手机在线状态和最近心跳时间。
- 单号码任务创建表单。
- 当前及历史任务列表。
- 任务状态时间线。
- 录音上传和处理状态。
- 转写文本。
- GPT-5.5 结构化结果。
- 失败原因和重试按钮。

页面通过 SSE 接收状态变化，断线后自动重连，并通过一次普通查询补齐当前状态。

## 6. 核心流程

1. 测试人员在网页输入手机号并创建任务。
2. 服务端将任务标记为 `PENDING`。
3. 手机心跳并轮询领取任务。
4. 服务端原子地将任务绑定到该设备，状态变为 `CLAIMED`。
5. 手机校验号码、权限、网络和当前通话状态。
6. 手机发起 SIM 拨号，依次上报 `DIALING`、`IN_CALL` 或失败结果。
7. 人工通过手机完成通话，OriginOS 自动录音。
8. 挂断后手机上报 `CALL_ENDED`，等待录音文件落盘。
9. 手机匹配新增录音；成功后上传，失败则进入 `RECORDING_NOT_FOUND`。
10. 服务端保存录音并进入 `TRANSCRIBING`。
11. 转写成功后进入 `ANALYZING`，调用 GPT-5.5。
12. 服务端校验模型 JSON，保存结果并将任务标记为 `COMPLETED`。
13. 所有状态通过 SSE 实时推送到测试页面。

## 7. 任务状态

- `PENDING`：等待手机领取。
- `CLAIMED`：已绑定手机。
- `DIALING`：正在发起拨号。
- `IN_CALL`：通话已建立。
- `CALL_ENDED`：通话结束，等待录音。
- `RECORDING_MATCHING`：正在匹配录音。
- `RECORDING_NOT_FOUND`：未自动找到录音，可人工选择。
- `UPLOADING`：正在上传录音。
- `TRANSCRIBING`：正在转写。
- `ANALYZING`：正在进行模型判断。
- `COMPLETED`：任务完成。
- `FAILED`：任务失败，保存明确错误码和错误信息。

任务状态只能按定义的状态机迁移。重试会增加尝试次数并记录事件，不会静默覆盖历史失败。

## 8. 核心数据

### 8.1 外呼任务

- 任务 ID。
- 手机号；页面默认脱敏显示。
- 设备 ID。
- 创建、领取、拨号、接通、挂断和完成时间。
- 当前状态和最后错误。
- 通话结果与通话时长。
- 重试次数。

### 8.2 录音

- 录音 ID、任务 ID。
- 原始文件名、格式、大小和校验值。
- 本地发现时间和服务端上传时间。
- 匹配依据和匹配置信度。
- 服务端保存位置。

### 8.3 分析结果

```json
{
  "summary": "本次通话摘要",
  "contact_result": "本人接听/他人接听/无人接听/拒接/号码异常",
  "willingness": "高/中/低/未知",
  "promise_to_pay": false,
  "promised_date": null,
  "dispute": false,
  "risk_flags": [],
  "needs_human_review": true,
  "next_action": "建议下一步操作"
}
```

服务端使用固定 JSON Schema 校验输出。模型响应不合法时允许一次纠正性重试；仍不合法则保留原始响应，并将任务置为可重试失败。

## 9. 接口边界

首版接口按资源划分：

- 设备心跳。
- 创建和查询任务。
- 手机领取任务。
- 上报通话事件。
- 上传录音。
- 触发或重试转写与分析。
- 查询任务结果。
- SSE 状态事件流。

语音转写与 GPT-5.5 均通过服务端适配器调用。业务流程只依赖统一的转写结果和分析 JSON，不依赖具体供应商请求格式，方便以后切换公司内部网关。

## 10. 异常处理

- **手机离线**：任务保持 `PENDING`，页面显示设备最后心跳。
- **手机正在通话**：不领取新任务或将任务安全退回队列。
- **权限不足**：停止拨号并展示缺失权限，不循环弹窗。
- **号码无效**：在拨号前拒绝任务并记录原因。
- **忙线、拒接、无人接听**：记录通话结果；如果系统未生成录音，则不进入无意义的录音等待。
- **录音文件写入延迟**：在限定时间内分段扫描，避免读取尚未完成的文件。
- **找不到录音**：提示人工选择文件，保留任务与通话元数据。
- **上传中断**：以任务 ID 和文件校验值保证幂等重试。
- **转写或模型失败**：保留原始录音和中间结果，使用退避策略重试。
- **SSE 断开**：页面重连后重新查询任务快照，避免状态丢失。
- **服务重启**：数据库保存任务状态，未完成任务可恢复处理。

## 11. 安全与合规边界

- 测试页面仅绑定本机或明确的测试网卡地址，不直接暴露公网。
- 模型密钥只通过服务端环境变量或本地安全配置提供。
- 日志不打印完整手机号、录音正文或密钥。
- 原始录音和转写按测试用途设置可配置的保留期限。
- 正式接入前必须加入合法授权、允许拨打时段、频率限制、停呼名单、录音告知、人工复核和完整审计。
- 模型只提供判断和建议；争议、投诉、身份不确定、敏感情况和低置信度结果必须标记人工复核。

## 12. 测试策略

### 12.1 Android 侧

- 号码校验、状态转换和录音候选排序使用单元测试。
- 用模拟服务端验证领取、重试和幂等行为。
- 在 iQOO Neo8 Pro 真机验证权限、自动拨号、通话状态和录音目录。

### 12.2 服务端

- 对任务领取并发、状态机、录音幂等上传和模型 JSON 校验进行自动化测试。
- 使用假的转写和模型适配器跑完整集成测试，避免测试依赖外部模型。
- 使用一份经过授权的测试录音验证真实转写和 GPT-5.5 适配器。

### 12.3 端到端

至少连续执行 5 次单号码测试，覆盖：

- 正常接通并完成分析。
- 拒接或无人接听。
- 自动找不到录音后人工选择成功。
- 上传暂时失败后重试成功。
- 模型暂时失败后重试成功。

## 13. 验收标准

- 测试页面创建任务后，专用手机在数秒级轮询周期内领取并自动拨号。
- 页面无需刷新即可看到主要状态变化。
- 正常通话挂断后，录音能自动匹配上传，或能通过人工选择继续处理。
- 页面最终展示转写文本和通过 Schema 校验的 GPT-5.5 结果。
- 失败任务显示明确原因，且适用时可安全重试。
- 连续 5 次端到端测试中，系统没有重复拨打同一任务或丢失录音与结果。

## 14. 后续演进

原型验证通过后，可按以下顺序演进：

1. 接入公司任务与客户系统。
2. 加入账号、角色、权限、审计和正式合规策略。
3. 支持多手机设备和受控任务队列。
4. 用 SIM/GSM/VoLTE 语音网关替代手机音频链路。
5. 增加实时语音识别、对话决策、语音合成和人工接管，实现完整机器人外呼。
